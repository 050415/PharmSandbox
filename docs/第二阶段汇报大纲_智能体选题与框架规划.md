# PharmSandbox 第二阶段汇报大纲

## 智能体选题、框架规划与实施方案

---

> **汇报主题：** PharmSandbox 药盘推演 —— 基于 GNN+LLM 双引擎的药物相互作用临床决策智能体
>
> **核心定位：** 面向多病共存（Polypharmacy）场景的用药安全智能体，融合图神经网络（GNN）预测能力与大语言模型（LLM）解释能力，为临床医生提供"检测→评分→推荐→续方"一站式决策支持。
>
> **本文用途：** 指导 PPT 制作与现场讲解，按要点分章节，每章标注 PPT 页数建议与讲解重点。

## 一、智能体选题及其框架规划

> **PPT 建议：4-5 页** | **讲解时长：3-4 分钟**

### 1.1 选题背景与问题定义（PPT 第 1 页）

**核心论点：多药联用的 DDI 风险是临床刚需，传统手段力不从心。**

| 维度 | 说明 |
|------|------|
| **临床痛点** | 全球 65 岁以上老年人中 ≥40% 服用 5 种以上药物，DDI 是导致可预防性 ADE（药物不良事件）的首要原因 |
| **传统局限** | 查阅说明书 / 咨询药师 — 耗时长、覆盖不全、缺乏个体化评估 |
| **技术窗口** | GNN 可建模大规模异构图谱中的药物关系；LLM 可生成临床可读的因果解释 |
| **选题理由** | 将 GNN 的预测能力与 LLM 的解释能力结合，构建一个"能检测、能解释、能推荐"的临床决策智能体，填补现有 CDSS 系统在 DDI 预测精度与可解释性上的空白 |

**讲解要点：**
- 用数据切入（多药联用普遍性 → DDI 危害性 → 临床工具缺失）
- 引出"智能体"概念：不是简单的查询系统，而是能自主推理、多层决策的 AI Agent

---

### 1.2 智能体定义与核心能力（PPT 第 2 页）

**PharmSandbox 智能体 = 感知层 + 决策层 + 行动层 三层架构的临床用药安全 Agent。**

```
用户输入 ──→ [感知层] ──→ [决策层] ──→ [行动层] ──→ 用户输出
             药物识别     GNN+规则+LLM   API+UI渲染    报告/建议
             症状提取     评分+推荐+续方
```

**智能体的四项核心能力：**

| 能力 | 技术支撑 | 智能体表现 |
|------|----------|------------|
| **感知** (Perceive) | DrugNER（中英文 NER + 剂量提取） | 理解自然语言药物输入，自动结构化 |
| **推理** (Reason) | RGCN 图神经网络 + 规则引擎 + LLM 知识库 | 三层 DDI 检测，逐层递进，互补验证 |
| **决策** (Decide) | RiskScorer + DrugRecommender + PrescriptionTrigger | 从检测到评分到推荐到续方，完整决策链 |
| **行动** (Act) | Flask API + 三端 UI（医生/药师/患者） | 输出可执行建议：替代药物、续方草稿、风险报告 |

**讲解要点：**
- 强调"智能体"区别于传统软件的四个特征：感知→推理→决策→行动闭环
- 每个能力对应项目中具体模块，体现工程落地

### 1.4 选题的创新点与差异化（PPT 第 4 页）

| 创新维度 | 现有方案 | PharmSandbox 智能体 |
|----------|----------|---------------------|
| **DDI 检测** | 单一规则库（如 Drugs.com API） | **三层融合**：LLM 知识库（金标准仲裁）+ GNN 预测（图谱推理）+ 规则引擎（副作用交集回退） |
| **可解释性** | 仅给出"有/无交互"二元判断 | **因果解释**：14 种 DDI 类型模板 + 药理机制 + 临床建议 + 严重度分级 |
| **个体化** | 不看患者特征 | **多维调整**：年龄、肝肾功能、化验指标、疾病史的动态风险加权 |
| **决策闭环** | 检测即结束 | **检测→评分→替代推荐→续方**完整链路，输出可执行临床建议 |
| **数据驱动** | 依赖静态数据库 | MIMIC-IV 真实世界 EHR 数据训练，TWOSIDES 作为金标准正样本，困难负样本挖掘提升模型判别力 |
| **多端覆盖** | 仅医生端 | 医生工作台 + 患者 H5 + 药师审核，三方联动 |

**讲解要点：**
- 每个创新点结合具体技术实现来讲，避免空谈概念
- "三层融合"是最大卖点，建议用一页单独展开（见下）

### 1.5 核心技术决策：三层 DDI 检测架构（PPT 第 5 页，可选）

```
输入药物对 (Drug A, Drug B)
          │
          ▼
┌─────────────────────────────────┐
│  第 0 层：LLM 知识库（金标准层） │  ← 最高优先级
│  · 80+ 已知临床 DDI 对          │
│  · 严重度：禁忌/重大/中等/轻微   │
│  · 结果：命中 → 直接输出，不进入下层 │
└──────────────┬──────────────────┘
               │ 未命中
               ▼
┌─────────────────────────────────┐
│  第 1 层：GNN 模型（增强推理层） │  ← 中等优先级
│  · RGCN 图神经网络预测           │
│  · AUC=0.918, F1=0.836          │
│  · 结果：概率 > 阈值 → 输出      │
└──────────────┬──────────────────┘
               │ 未命中 / GNN 不可用
               ▼
┌─────────────────────────────────┐
│  第 2 层：规则引擎（保底回退层） │  ← 基础保障
│  · SIDER 副作用交集比对          │
│  · 共同副作用数量 → 严重度判定   │
│  · 结果：始终有输出（兜底）      │
└─────────────────────────────────┘
```

**三层架构的优势：**
1. **精度递进**：LLM 知识库精准命中已知高危 DDI → GNN 覆盖知识库未收录的潜在 DDI → 规则引擎保证无遗漏
2. **鲁棒性**：GNN 模型故障时自动降级至规则引擎，系统不中断
3. **可解释性**：每一层都有独立的解释通道（知识库有道理解释、GNN 有注意力权重、规则有副作用清单）

**讲解要点：**
- 这是智能体推理的"心脏"，值得花 1-2 分钟讲透
- 类比：知识库 = 教科书（已知确定知识）、GNN = 科研推理（从数据中归纳规律）、规则 = 安全网（永远兜底）

### 2.3 模块间数据传递详表（PPT 第 8 页）

| 传递路径 | 数据类型 | 关键字段 | 传递方式 |
|----------|----------|----------|----------|
| 用户输入 → NER | 自由文本 | 中英文药物名、剂量描述 | HTTP POST Body |
| NER → DDI 检测 | `List[str]` | 标准化英文药名列表 | Python 函数调用 |
| DDI 检测 → 风险评分 | `List[DDIResult]` | 药物对、严重度、置信度 | SandboxEngine 内部传递 |
| DDI+患者 → 风险评分 | `DDIResult[] + PatientInfo` | 年龄、疾病、化验值 | RiskScorer.score() 参数 |
| 风险评分 → 替代推荐 | `float(risk_score)` | 风险分数（触发阈值 40） | 条件分支 |
| 替代推荐 → 综合报告 | `List[AltDrug]` | 替代药名、ATC、评分、理由 | 合并到报告 dict |
| 处方信息 → 续方检查 | `Prescription` | 药物、总量、频次、开始日期 | PrescriptionTrigger.check() |
| 综合报告 → 前端 | JSON | 所有模块结果聚合 | Flask jsonify() → HTTP Response |
| 前端 → 可视化 | JSON | Canvas/SVG 渲染数据 | JavaScript 解析 |

**讲解要点：**
- 快速过表，不逐行念
- 重点说明：各模块之间是**松耦合**的，任一模块故障不影响其他模块（如 GNN 不可用时规则引擎兜底）

│  └────┬─────┘    └────┬─────┘    └────┬─────┘    └────┬─────┘  │
│       │               │               │               │         │
│       ▼               ▼               ▼               ▼         │
│  ┌──────────────────────────────────────────────────────────┐   │

│  │                                                           │   │
│  │  策略 1: SIDER 重叠挖掘                                    │   │

│  └──────────────────────────────────────────────────────────┘   │
│                         │                                        │
│                         ▼                                        │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │              最终训练集 (正负比 1:1)                        │   │

**讲解要点：**
- 强调正负样本的质量决定了模型上限

## 四、智能体主要性能指标及其测试方案

> **PPT 建议：4-5 页** | **讲解时长：4-5 分钟**

### 4.1 GNN 模型性能指标（PPT 第 15 页）

**当前最佳成绩（测试集）：**

| 指标 | 值 | 含义 |
|------|-----|------|
| **AUC** | **0.9183** | 模型区分正负样本的整体能力强，>0.9 为优秀 |
| **F1 (Macro)** | **0.8362** | 正负类均衡后的综合评分，>0.8 达到实用水平 |
| **Accuracy** | **0.8501** | 整体预测正确率 85% |
| **Precision** | **0.8275** | 预测为 DDI 的样本中 82.75% 确实是 DDI（误报率 ~17%） |
| **Recall** | **0.8515** | 真实 DDI 中 85.15% 被模型识别（漏报率 ~15%） |
| **Specificity** | ~0.849 | 真实非 DDI 中 84.9% 被正确排除 |

**训练配置：**

| 超参数 | 值 | 说明 |
|--------|-----|------|
| hidden_dim | 64 | 节点嵌入维度 |
| num_layers | 2 | RGCN 卷积层数 |
| learning_rate | 0.003 | 初始学习率 |
| batch_size | 64 | 批次大小 |
| epochs | 30 (早停 patience=8) | 训练轮数 |
| loss | Focal Loss (α=0.75, γ=2.0) | 聚焦困难样本 |
| scheduler | CosineAnnealingLR | 余弦退火学习率 |
| optimizer | Adam | 自适应优化器 |
| 总参数量 | 1,147,266 (~115 万) | 轻量级，CPU 可推理 |

**讲解要点：**
- AUC=0.918 是核心卖点——在图级别 DDI 预测任务中属于 SOTA 级别
- Focal Loss 的选择说明了正负样本不均衡问题的解决方案
- 模型只有 115 万参数，轻量化设计使 CPU 推理成为可能

### 4.2 模型泛化性验证（PPT 第 16 页）

**三项泛化验证策略：**

```
┌─────────────────────────────────────────────────────────────┐
│               泛化性验证三策略                               │
│                                                              │
│  策略 1: 留出法 (Hold-out)                                    │
│    80% 训练 / 10% 验证 / 10% 测试                            │
│    → 避免数据泄露，保证测试集独立                             │
│                                                              │
│  策略 2: LLM 知识库独立验证                                   │
│    用 LLM 标注的 80+ 临床 DDI 对作为独立测试集               │
│    而非训练集 → 检验模型对"临床教科书级"DDI 的识别能力       │
│    → 评估脚本: scripts/evaluate_model.py                     │
│                                                              │
│  策略 3: 困难负样本挑战测试                                   │
│    MIMIC 高频共处方（临床安全组合）作为负样本                 │
│    → 检验模型能否区分"看起来像但实际安全的"药物组合          │
│    → 高特异性 = 不给临床医生添不必要的告警                   │
└─────────────────────────────────────────────────────────────┘
```

**讲解要点：**
- 泛化性 ≠ 测试集分数高，而要证明模型在未见过的场景下也有效
- LLM 知识库独立验证是关键：用临床医生信任的已知 DDI 来检验模型，建立信任
- 困难负样本的意义：减少误报，避免"狼来了"效应

### 4.4 智能体特有指标的评估体系（PPT 第 18 页）

**除 GNN 模型指标外，定义智能体层面的评估维度：**

| 评估维度 | 指标定义 | 测量方法 | 目标值 |
|----------|----------|----------|--------|
| **DDI 检出率** | 已知 DDI 的召回比例 | LLM 知识库 80+ 对全量测试 | ≥ 95% |
| **误报控制** | 临床安全组合被误判为 DDI 的比例 | MIMIC 高频共处方测试集 | ≤ 10% |
| **推荐采纳率** | 替代药推荐被医生采纳的比例 | 用户研究 / A/B 测试 | ≥ 60% |
| **推演耗时** | 从输入到完整报告的时间 | 计时 full_simulation() | CPU < 30s, GPU < 5s |
| **降级鲁棒性** | GNN 不可用时系统仍正常输出 | 关闭 GNN 后的功能测试 | 100%（规则兜底） |
| **解释满意度** | 医生对 DDI 解释的满意度评分 | Likert 5 分量表 | ≥ 4.0/5.0 |
| **知识覆盖度** | ATC 分类树可覆盖的药物比例 | SIDER 药物名匹配统计 | ≥ 90% (1,430/1,560) |

**讲解要点：**
- 区分"模型指标"（AUC、F1）和"智能体指标"（端到端体验）
- 智能体指标更贴近临床实际——检出率和误报率是医生最关心的
- 降级鲁棒性是生产系统必备：GNN 挂了系统不能崩

### 4.5 已知局限与改进方向（PPT 第 19 页，可选）

| 局限 | 影响 | 改进方向 |
|------|------|----------|
| GNN 仅预测二分类（有/无 DDI） | 无法区分 DDI 严重度 | 多分类/回归头输出严重度分数 |
| 药物特征为随机向量（缺 RDKit 时） | 药物相似性信息丢失 | 集成 RDKit 分子指纹或预训练分子表征 |
| LLM 知识库仅 80+ 对 | 覆盖面有限 | 从 DrugBank XML 批量抽取或 PubMed NER 自动挖掘 |
| 缺乏药物-食物/药物-疾病交互 | 临床场景不完整 | 扩展图谱关系类型 |
| ATC 替代推荐不考虑药物过敏 | 安全性隐患 | 在推荐管线中增加过敏检查层 |
| 仅支持英文药名（NER 翻译中文） | 中文药品目录不完整 | 扩充中文词典 → 引入药品电子监管码映射 |

**讲解要点：**
- 坦诚展示局限 → 体现学术严谨性
- 每个局限都有对应的改进方向 → 体现规划前瞻性

### 5.3 场景应用详解：从门诊到病房（PPT 第 22 页）

| 临床场景 | 用户 | 智能体行为 | 输入 | 输出 |
|----------|------|------------|------|------|
| **门诊开药** | 门诊医生 | 输入多药物 → 自动全配对 DDI 检测 → 风险评分 → 高危时弹出替代药建议 | 药物列表 + 患者年龄/性别 | DDI 告警 + 替代建议 + 风险报告 |
| **药师审方** | 临床药师 | 批量审核处方 → 标注高/中/低风险 → 一键生成审核报告 | 处方列表 | 审核报告（通过/建议修改/拒绝） |
| **住院查房** | 住院医生 | 连接 EHR → 自动提取当前用药 → 结合最新化验值评分 | 患者 ID | 动态风险变化趋势图 |
| **慢病续方** | 患者 + 社区医生 | 自动计算剩余天数 → 剩余 ≤3 天触发续方提醒 → 生成草稿 | 处方信息 | 续方草稿（医生确认后生效） |
| **患者自查** | 患者 | 输入症状 → 人体图解定位 → 自动上报医生 | 自然语言症状 | 安抚指导 + 器官图示 + 上报通知 |

**讲解要点：**
- 5 个场景覆盖了医疗的核心环节：诊前→诊中→诊后
- 每个场景标注"谁在用、用什么功能、输入什么、得到什么"，清晰直接

### 5.4 部署安全性与合规设计（PPT 第 23 页）

| 安全维度 | 措施 | 当前状态 |
|----------|------|----------|
| **患者隐私** | 不存储 PII，仅使用去标识化数据；模拟患者数据完全虚构 | ✅ 已实现 |
| **数据隔离** | 不同医疗机构的数据逻辑隔离（多租户架构） | 🔲 规划中 |
| **通信加密** | 生产环境启用 HTTPS + JWT 鉴权 | 🔲 规划中（当前 Flask HTTP 明文） |
| **审计日志** | 记录每次 DDI 查询、推荐采纳/拒绝、处方变更 | 🔲 规划中 |
| **模型版本管理** | 训练历史 JSON 记录每次训练的配置和指标 | ✅ 已实现 |
| **免责声明** | UI 和报告中明确标注"本系统仅供临床参考，不能替代医生判断" | ✅ 已实现 |
| **数据合规** | SIDER/TWOSIDES 等数据仅用于学术研究（CC BY-NC 许可证） | ✅ 已标注 |

**讲解要点：**
- 标注"已实现"和"规划中"的区别，体现实事求是的态度
- 免责声明在医疗 AI 中非常重要——既是法律要求，也是伦理底线

### 讲解策略建议
